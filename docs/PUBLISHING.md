# Publishing Notification Manager

This guide records the path from local debug builds to store-installed tests and, later, a public release. Check linked store and OAuth policies again before submitting: their requirements and prices can change. Do not put signing keys, passwords, OAuth tokens, private Calendar data, or reviewer credentials in this repository.

This Git repository is public. The OAuth **client ID**, Cloud project number, Chrome extension ID, and manifest **public** key are identifiers used by installed clients, not credentials. Keep `mcp-server.log`, local keystores, passwords, tokens, reviewer credentials, and exported Calendar data out of Git. If an actual credential ever enters Git history, removing it from the latest file is insufficient: revoke or rotate it, then assess history cleanup separately.

## Recommended rollout

1. **Store-installed for the owner:** Google Play **internal testing** for Android; Chrome Web Store **Private** visibility with the owner as a trusted tester. Keep the Google OAuth project in **Testing** and the owner's account on its test-user list. Both stores deliver updates, but neither product is available to the general public.
2. **Small invited beta:** Manually add each person's Google account to the applicable store tester list **and** the OAuth test-user list. Give them opt-in links. Their apps use their own primary Calendar and hidden Drive app-data folder, not the owner's account.
3. **Public availability:** Meet Play production testing requirements, switch store distribution to Public or Unlisted as appropriate, prepare OAuth production verification for Calendar scopes, and decide whether an independent product allowlist is needed.

Store installation and Google OAuth are separate gates. While the OAuth audience is in **Testing**, only listed test users can authorize Calendar/Drive access (up to 100 listed users). Consent for these scopes expires after seven days, so a tester may need to reconnect. An unlisted person might be able to install an Unlisted/public store item, but cannot connect while OAuth remains in Testing. Do not make a public listing that appears usable by everyone while most installers cannot connect. [Google OAuth audience rules](https://support.google.com/cloud/answer/15549945)

## Expected costs

- Google Play Console: **US$25 one-time** developer registration. [Play registration](https://support.google.com/googleplay/android-developer/answer/6112435)
- Chrome Web Store: a **one-time developer registration fee, generally US$5**; confirm the actual amount at checkout. [Chrome developer registration](https://developer.chrome.com/docs/webstore/register/)
- No separate store charge per update. A privacy-policy site can use low-cost or free hosting; a custom domain, if chosen, has a registrar-dependent annual cost.
- Standard Calendar and Drive API use is available without an additional charge within Google's quotas. Google has announced possible charges for usage above standard daily thresholds later in 2026, after notice. Monitor project usage if the audience grows. [Drive API limits and pricing](https://developers.google.com/workspace/drive/api/guides/limits), [Workspace API quota changes](https://developers.google.com/workspace/tools-safety)
- An approval backend is not needed for the first two stages. Hosting, operations, and privacy obligations would add cost if one is built later.

## Shared preparation

1. Keep Google Cloud project **411250810503** and its OAuth audience in **Testing** for the initial owner-only rollout. Confirm the owner's account appears under **Google Auth platform → Audience → Test users**. Keep Google Calendar API and Google Drive API enabled.
2. Publish a privacy policy describing use of the account's primary Calendar, Calendar moves, locally cached events, locally stored dismissals, and the dismissal/move metadata in the user's Drive `appDataFolder`. Explain revocation and data deletion. Make the store disclosures and OAuth consent screen consistent with actual code. The stores require accurate data-handling declarations. [Play Data safety](https://support.google.com/googleplay/android-developer/answer/10787469), [Chrome user-data policy](https://developer.chrome.com/docs/webstore/program-policies/policies)
3. Create a **dedicated reviewer/demo Google account** with a few events named `Test Event - 1`, `Test Event - 2`, and so on. Add it as an OAuth test user. Put reviewer access instructions in the stores' private review fields; never provide personal account credentials or commit demo credentials to Git. [Play app-access instructions](https://support.google.com/googleplay/android-developer/answer/9859455), [Chrome submission instructions](https://developer.chrome.com/docs/webstore/publish/)
4. Review requested scopes before OAuth verification. Android requests `calendar.readonly`, `calendar.events` for moves, and `drive.appdata`; the extension lists those same scopes in `chrome-extension/manifest.json`. Google documents `drive.appdata` as non-sensitive. Calendar user-data scopes may require sensitive-scope verification when released broadly. [Drive app-data scope](https://developers.google.com/workspace/drive/api/guides/appdata), [Calendar scopes](https://developers.google.com/workspace/calendar/api/auth), [OAuth verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification)

## Android: first store-installed build

Current repository state: `app/build.gradle.kts` uses package name `com.noanadeem.notificationmanager`, `versionCode = 5`, and `versionName = "1.4"`. Versions 1 (1.0) and 2 (1.1) have been released to internal testing. Version 5 is prepared as a signed **Android App Bundle (`.aab`)**, using the same upload key. The existing `app/build/outputs/apk/debug/app-debug.apk` is a **debug-signed APK** and is not the store release artifact. Increase `versionCode` for each later Play release. [Android signing guide](https://developer.android.com/studio/publish/app-signing), [app-bundle upload guide](https://developer.android.com/studio/publish/upload-bundle)

1. Register a Play Console developer account under the Google account intended to own the app long term. Complete identity verification and pay the fee.
2. Create **Notification Manager** in Play Console. Set the app category, free pricing, contact details, content declarations, and store listing as the dashboard requests. Prepare screenshots, icon, and a support contact. Do not include private Calendar content in screenshots. [Play app setup](https://support.google.com/googleplay/android-developer/answer/9859152)
3. In Android Studio, use **Build → Generate Signed Bundle / APK → Android App Bundle**. Create a dedicated upload keystore, store it and its passwords securely outside Git, choose the release variant, and generate the signed `.aab`. Enroll in **Play App Signing** when Play prompts. The upload key signs what is sent to Play; Play's **app-signing key** signs what users install. [Signing and Play App Signing](https://developer.android.com/studio/publish/app-signing)
4. Once Play shows its **app-signing certificate SHA-1** under **Protected with Play → Play Store protection → Protect app signing key → Manage Play app signing**, add an **Android OAuth client** in Cloud project 411250810503 for package `com.noanadeem.notificationmanager` and that SHA-1. Keep the existing debug-certificate OAuth client for local development. Register the Play **app-signing** certificate, not only the upload certificate. [Google Play services client authentication](https://developers.google.com/android/guides/client-auth)
5. In Play Console, open **Test and release → Testing → Internal testing**. Create an email tester list containing the intended Google account, upload the signed `.aab`, create a release, and share the opt-in link. Internal testing supports up to 100 testers and does not require the production closed-test milestone. [Play testing tracks](https://support.google.com/googleplay/android-developer/answer/9845334)
6. Confirm the installed Play build can authorize, read its own primary Calendar, move **only a newly created test event** if an integration check is needed, and sync a test dismissal to Drive. Do not touch existing personal events for release testing.

**Transition from the debug APK:** A Play-signed build normally cannot update the current debug-signed installation in place because the signing certificates differ. Before uninstalling the debug build, confirm dismissals and moves have synchronized. Drive-backed state can be restored after signing in to the Play build; local-only pending changes and local preferences may be lost. [Android signing behavior](https://developer.android.com/studio/publish/app-signing)

For a newly created **personal** Play developer account, production access currently requires a **closed test with at least 12 testers opted in continuously for 14 days**, followed by an application for production access. This requirement does **not** block the first internal test. [Play personal-account requirements](https://support.google.com/googleplay/android-developer/answer/14151465)

## Inviting other testers without a backend

For each person, add the person's Google account to **OAuth Test users**, add it to the relevant **Play internal/closed tester list** and/or **Chrome Private trusted testers**, and send the applicable store opt-in link. These lists do not automatically synchronize with each other. Chrome's `chrome.identity` normally uses the Chrome profile's Google account, so testers should install and connect from the intended profile.

An in-app **Request access** button could open an email or form, but it cannot safely approve itself into the stores or OAuth Testing. Manual invitations are simpler while the tester group is small. Avoid publishing the store listing publicly with OAuth still limited to a small test-user list: people would be able to install but not connect.

## Broad public launch and optional approval queue

1. Complete Play's applicable closed-testing/production-access process and switch the Android release to **Production**. Change Chrome to **Public** or **Unlisted** depending on whether it should appear in search. [Play personal-account testing](https://support.google.com/googleplay/android-developer/answer/14151465), [Chrome visibility](https://developer.chrome.com/docs/webstore/cws-dashboard-distribution/)
2. Prepare the Google Auth platform audience for **In production** and submit its Calendar scopes for verification. Expect to provide a verified domain, consistent branding/privacy policy, scope justifications, and a demonstration video. Google says sensitive-scope review typically takes **3–5 business days**, though end-to-end preparation can take longer. The Testing-only seven-day consent behavior is unsuitable for a polished public release. [Sensitive-scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification)
3. If you still want approved users only after OAuth becomes publicly available, implement a **server-held allowlist** with Google identity sign-in, an approval queue, and checks before Calendar/Drive operations. A whitelist embedded only in Android or extension code is not a secure access control. This adds a backend, hosting, privacy, and operational work; defer it until manual invitations become burdensome.

Google's OAuth **Testing** list is a practical beta gate, but it is separate from the stores. Moving OAuth to **In production** removes that test-user-list gate; an unverified app can still show warnings and face a lifetime user cap, so verification is the recommended route before broad availability. [OAuth audience limits](https://support.google.com/cloud/answer/15549945), [OAuth production readiness](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification)
