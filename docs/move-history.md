# Recent move history

The Android app, home-screen widget, and Chrome extension record a move **only after Google Calendar confirms the event update**. Existing moves from before this feature cannot be reconstructed reliably. The settings menu's **Events recently moved** list shows the ten newest records, with the event title, new start time, and move time.

Each record contains a random record ID, Calendar event ID, title, old and new start times, and move time. Both clients save it locally first and sync it through the signed-in account's hidden Google Drive `appDataFolder` using the existing `drive.appdata` permission. One immutable metadata marker is created per move. Clients merge records by random ID, so simultaneous moves on different devices do not overwrite each other. Each successful sync keeps the newest ten records and tries to delete older markers; failed cleanup is retried at the next sync. Records more than 30 days old are excluded. Local storage is capped at ten records per account. During a Drive outage, a successful Calendar move remains successful and its recent-move record stays local for a later retry. The sync warning reports the history failure separately.

The marker description is small (usually a few hundred bytes), so ten records are typically only a few kilobytes of payload plus Drive file metadata. Move-history reads use a name-filtered Drive listing. They run when either client refreshes and after its own move. Widget refreshes still follow the existing Wi-Fi-only schedule. No Calendar events are changed merely to display this history.

If a Drive move marker is malformed, clients log and skip that marker while continuing to sync valid records. They leave the malformed file untouched because its original move data cannot be safely reconstructed or pruned. If both dismissal and move-history sync fail during the same refresh, both failures appear in the sync warning.
